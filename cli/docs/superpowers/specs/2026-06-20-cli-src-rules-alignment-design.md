# CLI `src` 规则对齐重构

## Status

已完成设计讨论，等待文档审阅后再进入正式重构。

## 背景

当前 `src` 代码已经有一轮错误模型相关重构，也已经开始吸收新的 TypeScript 和项目规则，但整体仍然存在明显不一致：

- 一部分文件已经按“文件底部统一导出”收口，另一部分还残留旧风格。
- 一部分实现已经按“类型明确时不额外使用泛型”“禁用三目”“禁用 `switch`”调整，另一部分还没有完全收口。
- `errors`、`commands`、`features`、`tools`、`types` 内部的命名、模块边界、局部实现位置和注释密度仍然不统一。
- 当前工作区本身已经有未提交改动，因此这次重构必须保持强约束，只对 `src` 里与规则对齐直接相关的内容动手，不连带处理无关问题。

## 范围

本次重构只覆盖：

- `src/**/*`

本次不覆盖：

- `package.json`
- `tsconfig*`
- `eslint` 配置
- 根目录脚本
- `docs/**/*`
- `rules-project/**/*`

## 约束

- 以 `rules/technologies/typescript/*` 和 `rules/projects/*` 为唯一规则来源。
- 不修改当前需求无关内容。
- 不为未来变化提前扩展。
- 保持现有 CLI 行为不变。
- 只清理本次重构直接带来的问题。
- 交付前必须运行当前项目已有检查命令验证结果。

## 目标

- 让 `src` 内代码与当前 7 份规则的主要硬约束对齐。
- 收口模块边界、导出方式、命名方式和局部实现位置。
- 收口类型定义、参数约束、错误模型和过重实现。
- 收口语句写法、循环方式、分支方式和 TSDoc 结构。

## 非目标

- 不新增功能。
- 不调整 CLI 业务流程。
- 不把重构扩大到 `src` 之外。
- 不因为“可能以后会用到”新增抽象层、配置项或扩展点。

## 备选方案

### 方案一：一次性全量收口

按全部规则一次性扫完 `src`。

优点：

- 只做一轮，结束更快。

缺点：

- diff 过大，注释改动会淹没真正的代码重构。
- 当前工作区已经有未提交改动，风险最高。

### 方案二：按规则层次分三轮收口

第一轮处理 `结构与命名`，第二轮处理 `类型与实现`，第三轮处理 `语句与注释`。

优点：

- 每轮目标更单一，验证点更清晰。
- 更适合当前脏工作区。
- 更容易在每轮结束后判断是否偏离需求。

缺点：

- 需要分多轮推进。

### 方案三：按模块逐块收口

按 `errors -> tools -> features -> commands -> types/schemas` 分块改，每块内部同时处理全部规则。

优点：

- 单个模块的边界更完整。

缺点：

- 同类规则会在不同模块里反复切换。
- 全局一致性更难在中途检查。

## 设计决定

采用方案二：按规则层次分三轮收口。

原因：

- 当前规则本身分成命名、类型、实现、语句、注释几个维度，按规则层次推进更符合本次目标。
- 当前工作区已有未提交改动，分轮更容易控制风险和定位回归。
- 注释和 TSDoc 会显著放大 diff，放到最后处理更不容易干扰前两轮真正的结构重构。

## 重构设计

### 第一轮：结构与命名

这一轮只处理会直接影响模块边界和可读性的内容：

- 模块导出统一写在文件底部。
- 模块只导出真正对外使用的接口。
- 只被单个函数使用的数据就近定义。
- 固定配置对象、普通常量、对象式枚举、私有映射表的命名收口。
- 函数、方法、类、类型、接口命名按规则统一。
- 文件内私有实现的命名改成直接说明职责的写法。

这一轮不主动大改注释，只在移动或重命名代码时顺手修正最明显冲突。

### 第二轮：类型与实现

这一轮处理类型和实现复杂度：

- 参数类型只写实际输入。
- 对象类型用 `interface`，组合和派生类型用 `type`。
- 类型明确时去掉额外泛型。
- 不使用 `any`、`unknown` 兜底。
- `as` 只保留在“明确知道类型但 TypeScript 没推出来”的位置。
- 只为当前已确认边界编写逻辑。
- 把明显超过需求的实现改回更小、更直接的做法。
- 收口错误模型、命令对象、工具函数和局部实现的位置。

### 第三轮：语句与注释

这一轮最后处理风格层规则：

- `const` / `let` 按是否重赋值区分。
- 禁止三目运算符。
- 禁用 `switch`。
- 禁用 `for...in`、`for...of`、`for`、`while`、`do...while`，统一改成数组循环方法。
- 退出条件放在前面，优先早返回。
- TSDoc 补全 `@param`、`@returns`、`@throws`、`@example`。
- 类型、常量、配置、函数、类、方法统一使用 `/** */`。
- 函数体内部说明统一使用单行注释。

## 执行顺序

1. 第一轮先扫 `errors`、`types`、`tools` 这些基础层，收口结构与命名。
2. 再收口 `features`，最后收口 `commands`。
3. 第二轮按同样顺序处理类型与实现。
4. 第三轮最后统一收口语句与注释。

这样安排是因为上层 `commands` 依赖下层 `features / tools / errors / types`，先改基础层更稳。

## 检查点

### 检查点一：结构与命名

完成标准：

- 顶部声明、底部导出统一。
- 私有实现不再误导性导出。
- 主要命名与规则一致。
- 没有新增无意义中间层。

### 检查点二：类型与实现

完成标准：

- 明显不符合规则的可选参数、冗余泛型、过重抽象被收口。
- 错误模型和核心流程实现没有额外扩展。
- 现有行为保持不变。

### 检查点三：语句与注释

完成标准：

- 关键语句规则对齐完成。
- TSDoc 和注释结构符合规则。
- 没有为了补注释再引入与前两轮冲突的改动。

## 验证方式

每轮完成后做最小自检，最终统一运行：

```powershell
bun run check
```

如果过程中发现某一轮修改会影响行为判断，则补充针对该模块的定向检查，但不额外引入新的测试框架或测试文件。

## 风险与控制

### 风险一：当前工作区已有未提交改动

控制方式：

- 只改与规则对齐直接相关的内容。
- 不清理无关 diff。
- 每次修改前先读文件上下文，不覆盖已有用户改动。

### 风险二：注释规则会放大 diff

控制方式：

- 把注释和 TSDoc 放到第三轮最后处理。
- 前两轮不因为注释问题反复改同一个文件。

### 风险三：规则之间会互相影响

控制方式：

- 每轮结束后按“冲突、重复表达、职责混层”做一次自检。
- 一旦发现规则冲突，当轮一起收口，不把冲突留到后面。

## 最终建议

按“结构与命名 -> 类型与实现 -> 语句与注释”三轮推进，只覆盖 `src`，每轮完成后做检查点核对，最后统一运行 `bun run check` 验证结果。
