# Refine And Self Review

在“完善已有内容”或“询问还有什么可优化”的任务里，优先完成当前要求，再对结果做一次自审；如果本轮只是评估和补建议，则直接基于当前版本进入自审。

## 核心目标

把这类请求统一处理为两种路径：

1. 如果本轮包含实际修改、补齐、修复或实现，先完成用户要求，再审视更新后的结果。
2. 如果本轮只是评估和补建议，直接审视当前版本，判断是否还存在值得继续完善的空间。

不要只做执行不做自审，也不要在纯评估请求里假装已经执行了修改。

## 何时使用

在以下情况下启用本 skill：

- 用户要求完善已有项目内容，如“优化这段代码”“补充登录需求”“润色这份方案”“修复当前 bug”
- 用户要求在已有结果基础上继续改进，如“继续完善”“再优化一下”“还有什么可以改进”
- 用户要求继续实现、开发或补齐已有项目中的某一部分，如“继续完成订单模块”“把筛选功能补齐”“先把登录流程做完”
- 用户直接询问当前内容还可以怎么优化，如“还有哪些没做完”“下一步还能补什么”
- 用户希望拿到“完成结果 + 后续建议”的组合输出
- 用户接受上一轮自审建议，并要求“继续”“同意”“进行下一步”“按你的建议做”“执行下一步”等，且上下文明确指向上一轮建议

## 不使用的情况

在以下情况下，不强制追加自审段落：

- 用户明确要求“只给结果”“不要额外建议”
- 回复只是简短确认、问候、是/否回答
- 最终回复必须严格保持为机器可读格式或固定格式，如纯 JSON、纯补丁、严格表格
- 用户只要求返回代码本体，且额外自审说明会直接破坏当前交付格式

如果格式允许，优先追加单独的自审段落；如果格式不允许，就不要为了附加建议而破坏主输出格式。
即使省略自审段落，也应先完成一次内部自审，把能够直接修补的问题优先融入主输出，只是不额外展开说明。
代码任务默认也适用本 skill；只有在最终回复必须保持纯代码或纯补丁时，才省略自审段落。

## 执行流程

### 第 0 步：先定位当前目标

如果用户只说“继续完善”“再优化一下”“继续做”，但没有明确对象，先从当前上下文定位本轮要处理的文件、模块、页面、文档或方案。

如果从上下文仍无法明确当前目标，再向用户确认范围，不要在目标不清晰时贸然给出自审结论。

可使用类似话术：
`当前我还不能确定你要继续完善的是哪个文件、模块、页面或文档，请告诉我本轮目标。`

### 第 0.5 步：识别是否在承接上一轮自审建议

如果用户说“继续”“同意”“进行下一步”“按你的建议做”“执行下一步”等，而且上下文明确指向上一轮自审建议，默认视为执行请求，而不是再次解释建议。

处理规则：

- 如果上一轮建议本身是一组紧密相关、应该连续完成的步骤（如一组验证项），可以作为同一批下一步一起执行
- 如果上一轮有多条建议且彼此是互斥选择、范围差异明显，或无法合理默认其中一条，再向用户确认
- 如果不是成组步骤，也没有明显互斥关系，优先执行最相关、优先级最高、最直接可落地的那一条建议
- 如果上一轮建议是“验证、检查、打开、确认、对比、测试”等动作，必须实际执行；不要只写一份想象中的验证报告
- 执行完成后，把产出的最新结果当成新的当前版本，再进入后续自审

### 第 1 步：先完成用户要求

先解决用户当前要求的完善任务，例如：

- 补全文档缺失内容
- 优化方案结构
- 修复代码 bug
- 润色表达
- 修正逻辑错误

先把“该做的事”做完，不要跳过主任务直接给建议。
如果当前任务是在执行上一轮自审建议，就先把该建议真正落地，不要停留在复述、解释或改写建议本身。

如果用户本轮只是询问“还有什么可以优化”“还有哪些没做完”，则跳过本步，直接进入下一步做自审，不要假装本轮已经执行了修改。

### 第 2 步：对更新后的结果做自审

把已经完善后的结果，或刚执行完上一轮建议后的最新结果，当成当前版本，再检查一次：

- 是否还有明显遗漏
- 是否还有高优先级风险
- 是否还有可直接落地的进一步优化空间
- 是否已经达到“可以进入下一步”的状态

自审必须基于刚刚产出的最新结果，而不是泛泛而谈。

### 第 3 步：给出真实结论

只允许两种结论：

1. **仍有完善空间**
   给出 1-3 条具体、可执行、按优先级排序的进一步建议。
2. **当前已较完善**
   明确说明暂未发现高优先级改进项，并提醒用户可以进入下一步。

不要为了凑数硬写建议。

## 自审原则

### 应该做的

1. 先完成主任务，再做自审。
2. 建议必须基于当前结果中的真实缺口、风险或可提升点。
3. 建议要具体可执行，用户看到后可以直接继续让你动手。
4. 优先指出高价值问题，不要堆砌低价值建议。
5. 如果没有真实建议，就明确说“当前版本已可进入下一步”。
6. 自审建议优先聚焦当前任务直接相关的缺口，不要把范围扩展成整个项目的长期 roadmap。
7. 如果本轮只是评估和补建议，要明确这是基于当前版本的自审，而不是已执行修改后的结果。
8. 如果用户接受了上一轮自审建议，先执行该建议，再基于新结果继续自审。
9. 如果建议包含验证、检查、打开、确认、对比、测试等动作，要先实际执行，再写结论。

### 不应该做的

1. 重复主输出里已经写过的内容。
2. 给出空泛建议，如“还可以再优化一下”。
3. 明明没有问题却强行列出建议。
4. 用自审内容替代主任务结果。
5. 给出与当前项目内容无关的泛化建议。
6. 把“当前模块后续可补充的点”扩展成“整个项目未来所有可能功能”。
7. 用户已经要求“执行下一步”时，仍停留在解释建议、重复建议或只写计划。
8. 没有实际执行验证，却直接写“已通过”“已一致”“已完成验证”。

## 验证与结论置信度

自审结论必须和实际验证程度匹配：

1. 如果已经完成了必要验证，可以直接给出“当前已较完善”或“仍有完善空间”的结论。
2. 如果没有跑测试、没有执行验证步骤、没有核对完整上下文，也可以给出阶段性判断，但必须明确说明判断依据、未验证范围和残余风险。
3. 只有在未发现高优先级问题，且已说明验证范围时，才可以使用“在当前已验证范围内，已较完善，可以进入下一步”这类表述。
4. 不要把“暂时没看到问题”说成“已经完全没有问题”。
5. 如果上一轮建议本身就是验证动作，必须先完成验证，再给出验证结论；未执行时只能明确写成“待验证”或“无法验证”。

## 自审关注点

按输出类型调整自审重点：

| 输出类型 | 自审重点 |
| --- | --- |
| 代码 | 正确性、边界条件、异常处理、测试覆盖、可读性、潜在回归、是否需要补测试、是否需要手动验证步骤 |
| 需求文档 | 完整性、流程闭环、角色与权限、异常场景、验收标准、非功能需求、埋点、风控、权限边界 |
| 方案/架构 | 风险、回滚、扩展性、依赖项、成本、安全性 |
| 文档/说明 | 结构清晰度、表达准确性、示例完整性、读者可执行性 |
| 设计 | 交互闭环、一致性、可访问性、响应式、状态覆盖 |
| 通用项目内容 | 准确性、完整性、一致性、可落地性 |

## 输出方式建议

当格式允许，且自审结论确实对用户有帮助时，可在主输出后追加一个简短的自审结论块；这不是必须动作，也不要为了套模板而追加无价值内容。

优先级顺序如下：

1. 先服从用户要求的输出格式。
2. 再服从宿主环境或系统已有的回复风格。
3. 最后才参考本 skill 提供的推荐结构。

补充原则：

- 只有在存在真实、高价值的自审结论时才追加
- 默认尽量简短，避免重复主输出已经写过的内容
- 如果宿主环境已有固定结尾结构，不要硬套本 skill 的格式
- 如果最终输出必须是纯 JSON、纯补丁、纯代码或其他固定格式，则不要追加额外结论块
- 如果只是小修小补，且没有必要单独展开说明，也可以只做内部自审，不额外展示

### 推荐结构 A：执行后仍有完善空间

默认给 1 条建议；确有必要时再扩展到 2-3 条。
如果存在未验证部分，可补充 `验证说明` 和 `残余风险`。

```markdown
---

**自审结果**

当前版本已完成本次要求，但还有 1 个值得优先继续处理的点：[最重要、最具体的改进点]

**建议下一步：**
- [可直接执行的后续动作]
```

### 推荐结构 B：执行后当前已较完善

如果结论基于有限验证，可补充 `验证说明` 和 `残余风险`。

```markdown
---

**自审结果**

当前版本已完成本次要求，在当前已验证范围内，暂未发现需要优先继续处理的明显问题，可进入下一步。

**建议下一步：**
- [进入评审 / 测试 / 提交 / 验收等后续流程]
```

### 纯评估场景的写法

如果本轮只是回答“还有什么可以优化”“还有哪些没做完”，就把上面两种推荐结构中的“当前版本已完成本次要求”改成“基于当前版本评估”，不要假装已经执行了修改。

## 示例

### 示例 1：完善需求文档中的登录功能

用户说：完善这份需求文档里的登录功能。

正确做法：

1. 先补全登录功能需求，例如账号密码登录、错误提示、忘记密码、验证码、登录成功跳转、验收标准等。
2. 再自审当前需求文档是否还有缺口。
3. 如果发现仍缺少如“风控限制”或“异常场景”，就给出进一步建议。
4. 如果登录需求已经覆盖完整，就明确告诉用户当前版本可以进入评审或设计阶段。

### 示例 2：解决当前文件中的代码 bug

用户说：修复当前文件的 bug。

正确做法：

1. 先定位并修复 bug。
2. 再自审修复后的代码是否还存在边界条件、异常处理、测试缺失或潜在回归问题。
3. 如果仍有问题，就给出具体建议，例如“补一条空值分支测试”。
4. 如果没有明显问题，就说明在当前已验证范围内，当前代码已较完善，可以进入测试、提交或合并阶段。

### 示例 3：在 coding 项目中完成部分功能后继续自审

用户说：继续完成这个项目的订单管理模块，先把订单列表和筛选功能做出来。

正确做法：

1. 先实现用户当前要求的订单列表和筛选功能，确保本次需求范围内的代码已经完成。
2. 再自审当前模块，不仅检查本次实现是否可用，还要检查与该模块直接相关但尚未完成的功能或配套能力。
3. 如果发现仍有未完成内容，就明确告诉用户，例如“当前已完成订单列表和筛选，但分页、导出、批量操作、空状态、异常提示、权限控制或测试覆盖仍可继续完善”。
4. 自审建议要优先聚焦当前功能链路里最相关、最影响可交付性的缺口，不要泛泛列出整个项目所有未来功能。
5. 如果当前阶段目标已经完整覆盖，就说明在当前已验证范围内，该模块已可进入联调、测试或继续开发下一模块的阶段。

### 示例 4：重构代码后继续自审

用户说：把这个 service 重构一下，拆清楚职责，提升可维护性。

正确做法：

1. 先完成本次重构，例如拆分职责、优化命名、减少重复逻辑、理清模块边界。
2. 再自审重构后的代码，不仅检查结构是否更清晰，还要检查行为是否保持一致、是否引入潜在回归、是否需要补回归测试。
3. 如果仍有可继续完善的点，就给出具体建议，例如“当前职责拆分已完成，但异常处理仍分散在多个分支，建议继续收敛为统一错误处理入口”。
4. 如果存在验证不足，也应明确说明，例如“当前主要完成了静态重构，仍建议补充回归测试以确认外部行为未变化”。
5. 如果当前目标已经达到，就说明在当前已验证范围内，这次重构已可进入测试、评审或继续整理下一层模块。

### 示例 5：前端模块完善后继续自审

用户说：把用户中心页面完善一下，先补上资料编辑和头像上传功能。

正确做法：

1. 先完成资料编辑和头像上传这两个当前要求的前端功能。
2. 再自审当前页面，不仅检查功能是否能用，还要检查表单校验、loading 状态、错误提示、空状态、移动端适配、可访问性和交互闭环是否完整。
3. 如果仍有缺口，就给出具体建议，例如“当前编辑和上传功能已完成，但头像上传失败提示、保存中的禁用态、移动端布局和成功反馈仍可继续完善”。
4. 自审建议应优先聚焦当前页面和当前交互链路的缺口，不要扩展成整个前端系统的长期 UI 改造计划。
5. 如果当前范围已经覆盖完整，就说明在当前已验证范围内，该页面已可进入联调、测试或视觉走查阶段。

### 示例 6：用户直接询问还有什么可以优化

用户说：这个模块还有什么可以优化？

正确做法：

1. 不要假装本轮已经执行了修改，而是直接基于当前模块进入自审。
2. 先检查当前模块的真实状态，再给出 1-3 条最值得继续处理的改进建议。
3. 如果上下文足够，就直接给出聚焦当前模块的建议；如果上下文不足，就先定位当前模块范围，必要时再向用户确认。
4. 如果在当前已验证范围内暂未发现高优先级问题，也可以明确告诉用户当前版本已较完善，并建议进入下一步。

### 示例 7：用户明确要求只给结果，不要建议

用户说：把这段代码修掉，只给结果，不要额外建议。

正确做法：

1. 先完成用户要求的修复。
2. 仍可在内部做一次自审，把能直接修补的问题尽量融入主输出。
3. 但最终回复不要追加 `自审结果`、下一步建议或额外分析说明。

### 示例 8：最终输出必须保持纯 JSON / 纯补丁 / 纯代码

用户说：把结果按 JSON 返回，或者只输出 patch / 只输出代码。

正确做法：

1. 先完成当前要求，并在内部做一次自审。
2. 如果自审发现能直接修补的问题，应优先融入主输出。
3. 最终回复必须保持用户要求的固定格式，不要追加 `自审结果`、说明文字或额外建议段落。
4. 不要为了输出建议而破坏 JSON、补丁或纯代码格式。

### 示例 9：用户要求执行上一轮自审建议

用户说：执行下一步，验证原型图完整性、样式一致性和 PRD 是否同步。

正确做法：

1. 先把这句话识别为“执行上一轮自审建议”，而不是继续解释建议。
2. 实际打开、检查、核对相关文件或页面，收集真实验证依据。
3. 明确区分哪些项目已经验证，哪些还没有验证，哪些因为工具限制暂时无法验证。
4. 完成验证后，再基于最新结果做一轮新的自审，判断是否还存在高优先级缺口。
5. 如果当前已验证范围内没有明显问题，就说明可以进入下一步；如果仍有缺口，就给出新的下一步建议。

## 一句话准则

凡是“完善已有内容”的请求，默认按“先完成任务，再自审一次，再告诉用户是否还值得继续完善”来处理；如果用户接受上一轮自审建议，就先执行该建议，再基于最新结果继续自审；如果用户本轮只要求评估和建议，则直接基于当前版本进入自审。
