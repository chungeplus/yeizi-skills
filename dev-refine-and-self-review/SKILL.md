# Dev Refine And Self Review

这是一个面向软件开发全流程的 refine skill，覆盖需求、设计、研发、测试、联调、发布与交付阶段。

在“产出软件开发交付物”或“询问还有什么可优化”的任务里，优先完成当前要求，再对结果做一次自审；如果本轮只是评估和补建议，则直接基于当前版本进入自审。

## 核心目标

把这类请求统一处理为两种路径：

1. 如果本轮包含实际修改、补齐、修复或实现，先完成用户要求，再审视更新后的结果。
2. 如果本轮只是评估和补建议，直接审视当前版本，判断是否还存在值得继续完善的空间。

不要只做执行不做自审，也不要在纯评估请求里假装已经执行了修改。

## 触发逻辑（默认开启）

除非满足豁免条件，否则凡是涉及软件开发交付物的首次产出、修改、补齐、重做、重构、合并、迁移、换风格、继续推进或收尾整理任务，完成后都默认执行一次自审。

在软件开发场景中，这通常包括：

- 首版 PRD、首版原型、首版页面、首版接口、首版模块实现
- PRD、用户故事、流程图、验收标准、版本说明
- 原型、UI 页面、设计规范、组件样式
- 前端页面、组件、状态逻辑、接口联调
- 后端接口、服务、脚本、任务、数据库相关逻辑
- 测试用例、验证记录、联调结果、提测/发布说明

关键词只用于辅助判断，不是唯一触发方式；不要因为用户没说“优化/完善”就跳过自审。

### 豁免条件

在以下情况下，可不强制进入本 skill 的完整自审流程：

- 用户明确要求“只给结果”“不要建议”“不要额外内容”
- 最终输出必须严格保持为固定格式，如纯 JSON、纯补丁、纯代码、严格表格
- 本轮只是简单确认、问候、是/否回答、纯解释、纯分析或纯头脑风暴
- 改动极小且低风险，例如只改一个非关键文案、一个不影响逻辑的样式值

判断“极小改动”时，不要只看改了几行，更要看风险范围；即使只改一行，如果影响关键逻辑、权限、状态流转或核心布局，也不属于豁免场景。

## 何时使用

在以下情况下启用本 skill：

- 用户要求完善已有项目内容，如“优化这段代码”“补充登录需求”“润色这份方案”“修复当前 bug”
- 用户要求先产出某个软件开发交付物，如“先写一版 PRD”“先做一个登录页”“先起一个接口”“先把这个模块搭出来”
- 用户要求在已有结果基础上继续改进，如“继续完善”“再优化一下”“还有什么可以改进”
- 用户要求继续实现、开发或补齐已有项目中的某一部分，如“继续完成订单模块”“把筛选功能补齐”“先把登录流程做完”
- 用户要求重做、重构、改版、换风格、合并、迁移已有内容，如“把这 15 页都重做”“按这个风格重新来”“把原型合并成一个文件”
- 用户要求推进软件交付链路中的下一步，如“把这个 PRD 补到可评审”“把这个页面补到可联调”“把这个模块整理到可提测”
- 用户直接询问当前内容还可以怎么优化，如“还有哪些没做完”“下一步还能补什么”
- 用户希望拿到“完成结果 + 后续建议”的组合输出
- 用户接受上一轮自审建议，并要求“继续”“同意”“进行下一步”“按你的建议做”“执行下一步”等，且上下文明确指向上一轮建议

## 不使用的情况

在以下情况下，不强制追加自审段落：

- 用户明确要求“只给结果”“不要额外建议”
- 回复只是简短确认、问候、是/否回答
- 回复只是纯解释、纯分析、纯头脑风暴，且没有要求你落地修改现有内容
- 最终回复必须严格保持为机器可读格式或固定格式，如纯 JSON、纯补丁、严格表格
- 用户只要求返回代码本体，且额外自审说明会直接破坏当前交付格式
- 改动极小且低风险，如只改一个非关键文案或一个不影响逻辑的样式值

如果格式允许，优先追加单独的自审段落；如果格式不允许，就不要为了附加建议而破坏主输出格式。
即使省略自审段落，也应先完成一次内部自审，把能够直接修补的问题优先融入主输出，只是不额外展开说明。
代码任务默认也适用本 skill；只有在最终回复必须保持纯代码或纯补丁时，才省略自审段落。

## 角色视角选择

这是一个软件开发全流程 skill。触发后，先根据当前交付物选择主视角，再按需要补充次视角检查。

主视角优先按最终交付物判断：

- PRD、需求说明、流程设计、验收标准、版本范围：产品 / 需求视角
- 原型、页面、组件、视觉规范、交互稿：设计 / 前端 UI 视角
- 前端代码、后端代码、接口、服务、脚本、任务实现：研发视角
- 技术方案、架构拆分、选型、依赖治理：架构 / 技术方案视角
- 测试用例、验证报告、联调结果、走查结论：测试 / 验证视角
- 提测说明、发布说明、交付清单、对齐状态：项目推进 / 交付视角

如果一个任务同时涉及多个角色：

- 主视角只保留一个，以最终交付物为准
- 次视角只补与当前交付直接相关的检查，不要把一次自审扩展成整个项目的全角色巡检

## 多交付物联动检查

如果本轮同时修改了多个交付物，不要只检查单个文件或单个页面本身，还要检查这些交付物之间是否同步。

常见联动组合包括：

- PRD + 原型
- 原型 + 页面实现
- 页面实现 + 接口 / 数据结构
- 测试记录 + 联调结果 + 提测说明
- 发布说明 + 交付清单 + 实际产物路径

至少检查以下联动项：

- 名称是否一致，如模块名、页面名、接口名、版本名
- 数量是否一致，如页面数、接口数、步骤数、清单项数
- 路径或引用是否一致，如文件路径、链接、接口地址、资源引用
- 状态是否一致，如“已完成 / 待联调 / 待提测 / 已发布”等标记
- 版本与范围是否一致，如 PRD、原型、页面实现、发布说明是否仍指向同一版本范围

如果多交付物之间存在不同步，不要只给局部通过结论，应优先把“同步缺口”列为自审结果。

## 执行流程

### 第 0 步：先定位当前目标

如果用户只说“继续完善”“再优化一下”“继续做”，但没有明确对象，先从当前上下文定位本轮要处理的文件、模块、页面、文档或方案。

如果从上下文仍无法明确当前目标，再向用户确认范围，不要在目标不清晰时贸然给出自审结论。

可使用类似话术：
`当前我还不能确定你要继续完善的是哪个文件、模块、页面或文档，请告诉我本轮目标。`

### 第 0.5 步：识别是否在承接上一轮自审建议

如果用户说“继续”“同意”“进行下一步”“按你的建议做”“执行下一步”等，而且上下文明确指向上一轮自审建议，默认视为执行请求，而不是再次解释建议。

处理规则：

- 如果上一轮建议本身是一组紧密相关、应该连续完成的步骤（如一组验证项），可以作为同一批下一步一起执行
- 如果上一轮有多条建议且彼此是互斥选择、范围差异明显，或无法合理默认其中一条，再向用户确认
- 如果不是成组步骤，也没有明显互斥关系，优先执行最相关、优先级最高、最直接可落地的那一条建议
- 如果上一轮建议是“验证、检查、打开、确认、对比、测试”等动作，必须实际执行；不要只写一份想象中的验证报告
- 执行完成后，把产出的最新结果当成新的当前版本，再进入后续自审

### 第 1 步：先完成用户要求

先解决用户当前要求的完善任务，例如：

- 补全文档缺失内容
- 优化方案结构
- 修复代码 bug
- 润色表达
- 修正逻辑错误

先把“该做的事”做完，不要跳过主任务直接给建议。
如果当前任务是在执行上一轮自审建议，就先把该建议真正落地，不要停留在复述、解释或改写建议本身。

如果用户本轮只是询问“还有什么可以优化”“还有哪些没做完”，则跳过本步，直接进入下一步做自审，不要假装本轮已经执行了修改。

### 第 2 步：对更新后的结果做自审

把已经完善后的结果，或刚执行完上一轮建议后的最新结果，当成当前版本，再检查一次：

- 是否还有明显遗漏
- 是否还有高优先级风险
- 是否还有可直接落地的进一步优化空间
- 是否已经达到“可以进入下一步”的状态

自审必须基于刚刚产出的最新结果，而不是泛泛而谈。

### 第 3 步：给出真实结论

只允许两种结论：

1. **仍有完善空间**
   给出 1-3 条具体、可执行、按优先级排序的进一步建议。
2. **当前已较完善**
   明确说明暂未发现高优先级改进项，并提醒用户可以进入下一步。

不要为了凑数硬写建议。

## 自审原则

### 应该做的

1. 先完成主任务，再做自审。
2. 建议必须基于当前结果中的真实缺口、风险或可提升点。
3. 建议要具体可执行，用户看到后可以直接继续让你动手。
4. 优先指出高价值问题，不要堆砌低价值建议。
5. 如果没有真实建议，就明确说“当前版本已可进入下一步”。
6. 自审建议优先聚焦当前任务直接相关的缺口，不要把范围扩展成整个项目的长期 roadmap。
7. 如果本轮只是评估和补建议，要明确这是基于当前版本的自审，而不是已执行修改后的结果。
8. 如果用户接受了上一轮自审建议，先执行该建议，再基于新结果继续自审。
9. 如果建议包含验证、检查、打开、确认、对比、测试等动作，要先实际执行，再写结论。

### 不应该做的

1. 重复主输出里已经写过的内容。
2. 给出空泛建议，如“还可以再优化一下”。
3. 明明没有问题却强行列出建议。
4. 用自审内容替代主任务结果。
5. 给出与当前项目内容无关的泛化建议。
6. 把“当前模块后续可补充的点”扩展成“整个项目未来所有可能功能”。
7. 用户已经要求“执行下一步”时，仍停留在解释建议、重复建议或只写计划。
8. 没有实际执行验证，却直接写“已通过”“已一致”“已完成验证”。

## 验证与结论置信度

自审结论必须和实际验证程度匹配：

1. 如果已经完成了必要验证，可以直接给出“当前已较完善”或“仍有完善空间”的结论。
2. 如果没有跑测试、没有执行验证步骤、没有核对完整上下文，也可以给出阶段性判断，但必须明确说明判断依据、未验证范围和残余风险。
3. 只有在未发现高优先级问题，且已说明验证范围时，才可以使用“在当前已验证范围内，已较完善，可以进入下一步”这类表述。
4. 不要把“暂时没看到问题”说成“已经完全没有问题”。
5. 如果上一轮建议本身就是验证动作，必须先完成验证，再给出验证结论；未执行时只能明确写成“待验证”或“无法验证”。
6. 如果采用抽样审查，必须明确说明抽样范围、未覆盖范围和残余风险；不要把抽样结论说成全量审查结论。

## 验证证据来源

在写“已验证范围内”这类结论前，先明确你的证据来自哪里。可使用一种或多种来源：

- 静态检查：阅读代码、文档、配置、页面结构、样式结构得到的判断
- 运行结果：本地运行、构建结果、命令输出、接口响应、日志输出
- 浏览器 / 页面查看：页面渲染、布局、交互状态、滚动、可见性检查
- 测试输出：单测、集成测试、回归测试、手动验证记录
- 文档核对：PRD、原型、实现、测试说明、交付清单之间的对照
- 人工走查：基于当前上下文做的结构检查、路径核对、状态核对

输出结论时，尽量让验证说明和证据来源对应：

- 不要把“静态检查”写成“已实际运行验证”
- 不要把“抽样查看几个页面”写成“已全量验证”
- 不要把“文档核对通过”写成“功能已经可用”

## 角色化自审关注点

按主视角调整自审重点。维度保持抽象，典型症状帮助你识别常见失败模式；症状列表不是穷尽式 checklist，应结合当前项目阶段和交付物判断：

| 角色视角 | 典型任务 / 交付物 | 自审重点 | 典型症状（自审时重点排查） |
| --- | --- | --- | --- |
| 产品 / 需求 | PRD、用户故事、流程、验收标准、版本说明 | 闭环完整性、角色权限、异常流程、范围边界、验收口径 | 有主流程无异常流程、有功能无验收标准、有角色无权限边界、版本范围漂移、文档和原型不一致 |
| 设计 / 前端 UI | 原型、页面、组件、设计规范、交互稿 | 布局完整性、交互闭环、视觉一致性、状态覆盖、响应式 | 元素超出页面边界、底部异常空白滚动、固定元素遮挡、点击无反馈、同类组件样式不一致、旧风格残留 |
| 研发实现 | 前端代码、后端代码、接口、服务、脚本、任务实现 | 运行时风险、边界条件、异常处理、回归风险、可维护性 | `null`/`undefined` 未处理、异步竞态、状态未复位、重复逻辑、魔法数字、补丁式分支堆积 |
| 架构 / 技术方案 | 技术方案、架构拆分、选型、依赖治理 | 风险覆盖、回滚与降级、扩展性、依赖边界、成本与安全 | 有方案无回滚、有依赖无降级、扩展点无约束、职责边界模糊、成本上限不清、安全边界未说明 |
| 测试 / 验证 | 测试用例、验证记录、联调结论、走查结果 | 验证范围、证据充分性、通过条件、遗漏风险 | 只写结论不写依据、未区分已验证/未验证、抽样结论写成全量结论、联调问题无复现路径 |
| 项目推进 / 交付 | 提测说明、发布说明、交付清单、状态同步 | 交付物一致性、依赖对齐、状态同步、下一步明确性 | 文档与实际产物不一致、路径/版本号未同步、提测条件不清、责任边界不清、下一步缺 owner 或缺入口 |

## 大产出抽样审查

当产出明显大到全量审查成本过高时，可采用抽样策略做自审。以下阈值仅作参考，不是硬性门槛：

- 代码：约 300 行以上
- HTML/CSS：约 500 行以上
- 文档：约 1000 字以上

### 抽样规则

1. 必查项：
   - 入口/出口逻辑，如函数开头与返回、页面首屏与底部关键区域
   - 声明/定义区，如 `import`、全局状态、CSS 变量、配置区
   - 首尾结构，如 HTML 头部与闭合标签、模块边界、文档开头与结尾
   - 共享样式或公共能力，如公共组件、布局骨架、主题变量
2. 抽样项：
   - 额外抽取 2-3 个代表性中段或模块
   - 尽量覆盖不同类型内容，如表单页 + 列表页 + 详情页，或初始化逻辑 + 主流程 + 异常分支
   - 避免只检查相邻段落，避免样本过于单一
3. 说明义务：
   - 在自审结论中明确写出本次是全量审查还是抽样审查
   - 如果是抽样审查，明确写出覆盖范围、未覆盖范围和残余风险

如果用户明确要求严格验证、全量检查或高置信度结论，不要默认抽样，应优先执行更完整的审查。

## 输出方式建议

当格式允许，且自审结论确实对用户有帮助时，可在主输出后追加一个简短的自审结论块；这不是必须动作，也不要为了套模板而追加无价值内容。

优先级顺序如下：

1. 先服从用户要求的输出格式。
2. 再服从宿主环境或系统已有的回复风格。
3. 最后才参考本 skill 提供的推荐结构。

补充原则：

- 只有在存在真实、高价值的自审结论时才追加
- 默认尽量简短，避免重复主输出已经写过的内容
- 如果宿主环境已有固定结尾结构，不要硬套本 skill 的格式
- 如果最终输出必须是纯 JSON、纯补丁、纯代码或其他固定格式，则不要追加额外结论块
- 如果只是小修小补，且没有必要单独展开说明，也可以只做内部自审，不额外展示

### 推荐结构 A：执行后仍有完善空间

默认给 1 条建议；确有必要时再扩展到 2-3 条。
如果存在未验证部分，可补充 `审查范围`、`验证说明` 和 `残余风险`。

```markdown
---

**自审结果**

当前版本已完成本次要求，但还有 1 个值得优先继续处理的点：[最重要、最具体的改进点]

**建议下一步：**
- [可直接执行的后续动作]
```

### 推荐结构 B：执行后当前已较完善

如果结论基于有限验证，可补充 `审查范围`、`验证说明` 和 `残余风险`。

```markdown
---

**自审结果**

当前版本已完成本次要求，在当前已验证范围内，暂未发现需要优先继续处理的明显问题，可进入下一步。

**建议下一步：**
- [进入评审 / 测试 / 提交 / 验收等后续流程]
```

### 纯评估场景的写法

如果本轮只是回答“还有什么可以优化”“还有哪些没做完”，就把上面两种推荐结构中的“当前版本已完成本次要求”改成“基于当前版本评估”，不要假装已经执行了修改。

## 示例

### 示例 1：完善需求文档中的登录功能

用户说：完善这份需求文档里的登录功能。

正确做法：

1. 先补全登录功能需求，例如账号密码登录、错误提示、忘记密码、验证码、登录成功跳转、验收标准等。
2. 再自审当前需求文档是否还有缺口。
3. 如果发现仍缺少如“风控限制”或“异常场景”，就给出进一步建议。
4. 如果登录需求已经覆盖完整，就明确告诉用户当前版本可以进入评审或设计阶段。

### 示例 2：解决当前文件中的代码 bug

用户说：修复当前文件的 bug。

正确做法：

1. 先定位并修复 bug。
2. 再自审修复后的代码是否还存在边界条件、异常处理、测试缺失或潜在回归问题。
3. 如果仍有问题，就给出具体建议，例如“补一条空值分支测试”。
4. 如果没有明显问题，就说明在当前已验证范围内，当前代码已较完善，可以进入测试、提交或合并阶段。

### 示例 3：在 coding 项目中完成部分功能后继续自审

用户说：继续完成这个项目的订单管理模块，先把订单列表和筛选功能做出来。

正确做法：

1. 先实现用户当前要求的订单列表和筛选功能，确保本次需求范围内的代码已经完成。
2. 再自审当前模块，不仅检查本次实现是否可用，还要检查与该模块直接相关但尚未完成的功能或配套能力。
3. 如果发现仍有未完成内容，就明确告诉用户，例如“当前已完成订单列表和筛选，但分页、导出、批量操作、空状态、异常提示、权限控制或测试覆盖仍可继续完善”。
4. 自审建议要优先聚焦当前功能链路里最相关、最影响可交付性的缺口，不要泛泛列出整个项目所有未来功能。
5. 如果当前阶段目标已经完整覆盖，就说明在当前已验证范围内，该模块已可进入联调、测试或继续开发下一模块的阶段。

### 示例 4：重构代码后继续自审

用户说：把这个 service 重构一下，拆清楚职责，提升可维护性。

正确做法：

1. 先完成本次重构，例如拆分职责、优化命名、减少重复逻辑、理清模块边界。
2. 再自审重构后的代码，不仅检查结构是否更清晰，还要检查行为是否保持一致、是否引入潜在回归、是否需要补回归测试。
3. 如果仍有可继续完善的点，就给出具体建议，例如“当前职责拆分已完成，但异常处理仍分散在多个分支，建议继续收敛为统一错误处理入口”。
4. 如果存在验证不足，也应明确说明，例如“当前主要完成了静态重构，仍建议补充回归测试以确认外部行为未变化”。
5. 如果当前目标已经达到，就说明在当前已验证范围内，这次重构已可进入测试、评审或继续整理下一层模块。

### 示例 5：前端模块完善后继续自审

用户说：把用户中心页面完善一下，先补上资料编辑和头像上传功能。

正确做法：

1. 先完成资料编辑和头像上传这两个当前要求的前端功能。
2. 再自审当前页面，不仅检查功能是否能用，还要检查表单校验、loading 状态、错误提示、空状态、移动端适配、可访问性和交互闭环是否完整。
3. 如果仍有缺口，就给出具体建议，例如“当前编辑和上传功能已完成，但头像上传失败提示、保存中的禁用态、移动端布局和成功反馈仍可继续完善”。
4. 自审建议应优先聚焦当前页面和当前交互链路的缺口，不要扩展成整个前端系统的长期 UI 改造计划。
5. 如果当前范围已经覆盖完整，就说明在当前已验证范围内，该页面已可进入联调、测试或视觉走查阶段。

### 示例 6：用户直接询问还有什么可以优化

用户说：这个模块还有什么可以优化？

正确做法：

1. 不要假装本轮已经执行了修改，而是直接基于当前模块进入自审。
2. 先检查当前模块的真实状态，再给出 1-3 条最值得继续处理的改进建议。
3. 如果上下文足够，就直接给出聚焦当前模块的建议；如果上下文不足，就先定位当前模块范围，必要时再向用户确认。
4. 如果在当前已验证范围内暂未发现高优先级问题，也可以明确告诉用户当前版本已较完善，并建议进入下一步。

### 示例 7：用户明确要求只给结果，不要建议

用户说：把这段代码修掉，只给结果，不要额外建议。

正确做法：

1. 先完成用户要求的修复。
2. 仍可在内部做一次自审，把能直接修补的问题尽量融入主输出。
3. 但最终回复不要追加 `自审结果`、下一步建议或额外分析说明。

### 示例 8：最终输出必须保持纯 JSON / 纯补丁 / 纯代码

用户说：把结果按 JSON 返回，或者只输出 patch / 只输出代码。

正确做法：

1. 先完成当前要求，并在内部做一次自审。
2. 如果自审发现能直接修补的问题，应优先融入主输出。
3. 最终回复必须保持用户要求的固定格式，不要追加 `自审结果`、说明文字或额外建议段落。
4. 不要为了输出建议而破坏 JSON、补丁或纯代码格式。

### 示例 9：用户要求执行上一轮自审建议

用户说：执行下一步，验证原型图完整性、样式一致性和 PRD 是否同步。

正确做法：

1. 先把这句话识别为“执行上一轮自审建议”，而不是继续解释建议。
2. 实际打开、检查、核对相关文件或页面，收集真实验证依据。
3. 明确区分哪些项目已经验证，哪些还没有验证，哪些因为工具限制暂时无法验证。
4. 完成验证后，再基于最新结果做一轮新的自审，判断是否还存在高优先级缺口。
5. 如果当前已验证范围内没有明显问题，就说明可以进入下一步；如果仍有缺口，就给出新的下一步建议。

### 示例 10：大体量 UI 重构后的抽样自审

用户说：把这 15 页都换成清新自然风，按这个风格重新来。

正确做法：

1. 这类“重做 / 改版 / 换风格”任务即使没有出现“优化/完善”等关键词，也默认属于本 skill 的触发范围。
2. 先完成当前 UI 重构任务。
3. 如果产出体量很大，可采用抽样自审：先检查公共样式、主题变量、页面首尾结构，再抽取 2-3 个代表性页面做重点检查。
4. 自审时优先排查症状级问题，例如页面边界溢出、底部异常空白、固定元素遮挡、同类组件样式不一致、旧风格残留。
5. 输出结论时明确说明本次审查范围；如果只是抽样检查，不要把结论写成“已全量验证”。

### 示例 11：首版创建任务也要自审

用户说：先写一版登录模块 PRD，再补一个首版页面原型。

正确做法：

1. 这类“先做一版 / 先起一个 / 先搭出来”的首版创建任务，也属于本 skill 的默认触发范围。
2. 先完成当前 PRD 和原型的首版产出。
3. 再从产品 / 需求视角和设计 / 前端 UI 视角做自审，检查闭环、异常流程、页面入口出口、关键状态是否缺失。
4. 因为本轮同时改了 PRD 和原型，还要检查名称、页面数量、流程步骤、版本范围是否同步。

### 示例 12：多交付物联动检查

用户说：我把 PRD、原型和页面实现都补完了，你看看还能不能进入联调。

正确做法：

1. 不要只检查页面实现本身，还要把 PRD、原型、页面实现当成联动交付一起检查。
2. 优先核对名称、数量、路径、状态、版本范围是否一致。
3. 如果页面已经做完，但 PRD 页面数没同步、原型路径还指向旧文件、提测状态写错，就应先指出这些同步缺口。
4. 只有在多交付物之间基本对齐后，才可以给出“可以进入联调”的结论。

## 一句话准则

凡是涉及已有内容修改、补齐、重做、重构、合并、迁移、换风格或继续推进的请求，默认按“先完成任务，再自审一次，再告诉用户是否还值得继续完善”来处理；如果用户接受上一轮自审建议，就先执行该建议，再基于最新结果继续自审；如果产出过大，可采用抽样审查但必须说明范围；如果用户本轮只要求评估和建议，则直接基于当前版本进入自审。
