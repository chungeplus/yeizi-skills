# 完整示例

## 示例 1：完善需求文档中的登录功能

用户说：完善这份需求文档里的登录功能。

正确做法：

1. 先补全登录功能需求，例如账号密码登录、错误提示、忘记密码、验证码、登录成功跳转、验收标准等。
2. 再自审当前需求文档是否还有缺口。
3. 如果发现仍缺少如“风控限制”或“异常场景”，就给出进一步建议。
4. 如果登录需求已经覆盖完整，就明确告诉用户当前版本可以进入评审或设计阶段。

## 示例 2：解决当前文件中的代码 bug

用户说：修复当前文件的 bug。

正确做法：

1. 先定位并修复 bug。
2. 再自审修复后的代码是否还存在边界条件、异常处理、测试缺失或潜在回归问题。
3. 如果仍有问题，就给出具体建议，例如“补一条空值分支测试”。
4. 如果没有明显问题，就说明在当前已验证范围内，当前代码已较完善，可以进入测试、提交或合并阶段。

## 示例 3：在 coding 项目中完成部分功能后继续自审

用户说：继续完成这个项目的订单管理模块，先把订单列表和筛选功能做出来。

正确做法：

1. 先实现用户当前要求的订单列表和筛选功能，确保本次需求范围内的代码已经完成。
2. 再自审当前模块，不仅检查本次实现是否可用，还要检查与该模块直接相关但尚未完成的功能或配套能力。
3. 如果发现仍有未完成内容，就明确告诉用户，例如“当前已完成订单列表和筛选，但分页、导出、批量操作、空状态、异常提示、权限控制或测试覆盖仍可继续完善”。
4. 自审建议要优先聚焦当前功能链路里最相关、最影响可交付性的缺口，不要泛泛列出整个项目所有未来功能。
5. 如果当前阶段目标已经完整覆盖，就说明在当前已验证范围内，该模块已可进入联调、测试或继续开发下一模块的阶段。

## 示例 4：重构代码后继续自审

用户说：把这个 service 重构一下，拆清楚职责，提升可维护性。

正确做法：

1. 先完成本次重构，例如拆分职责、优化命名、减少重复逻辑、理清模块边界。
2. 再自审重构后的代码，不仅检查结构是否更清晰，还要检查行为是否保持一致、是否引入潜在回归、是否需要补回归测试。
3. 如果仍有可继续完善的点，就给出具体建议，例如“当前职责拆分已完成，但异常处理仍分散在多个分支，建议继续收敛为统一错误处理入口”。
4. 如果存在验证不足，也应明确说明，例如“当前主要完成了静态重构，仍建议补充回归测试以确认外部行为未变化”。
5. 如果当前目标已经达到，就说明在当前已验证范围内，这次重构已可进入测试、评审或继续整理下一层模块。

## 示例 5：前端模块完善后继续自审

用户说：把用户中心页面完善一下，先补上资料编辑和头像上传功能。

正确做法：

1. 先完成资料编辑和头像上传这两个当前要求的前端功能。
2. 再自审当前页面，不仅检查功能是否能用，还要检查表单校验、loading 状态、错误提示、空状态、移动端适配、可访问性和交互闭环是否完整。
3. 如果仍有缺口，就给出具体建议，例如“当前编辑和上传功能已完成，但头像上传失败提示、保存中的禁用态、移动端布局和成功反馈仍可继续完善”。
4. 自审建议应优先聚焦当前页面和当前交互链路的缺口，不要扩展成整个前端系统的长期 UI 改造计划。
5. 如果当前范围已经覆盖完整，就说明在当前已验证范围内，该页面已可进入联调、测试或视觉走查阶段。

## 示例 6：用户直接询问还有什么可以优化

用户说：这个模块还有什么可以优化？

正确做法：

1. 不要假装本轮已经执行了修改，而是直接基于当前模块进入自审。
2. 先检查当前模块的真实状态，再给出 1-3 条最值得继续处理的改进建议。
3. 如果上下文足够，就直接给出聚焦当前模块的建议；如果上下文不足，就先定位当前模块范围，必要时再向用户确认。
4. 如果在当前已验证范围内暂未发现高优先级问题，也可以明确告诉用户当前版本已较完善，并建议进入下一步。

## 示例 7：用户明确要求只给结果，不要建议

用户说：把这段代码修掉，只给结果，不要额外建议。

正确做法：

1. 先完成用户要求的修复。
2. 仍可在内部做一次自审，把能直接修补的问题尽量融入主输出。
3. 但最终回复不要追加 `自审结果`、下一步建议或额外分析说明。

## 示例 8：最终输出必须保持纯 JSON / 纯补丁 / 纯代码

用户说：把结果按 JSON 返回，或者只输出 patch / 只输出代码。

正确做法：

1. 先完成当前要求，并在内部做一次自审。
2. 如果自审发现能直接修补的问题，应优先融入主输出。
3. 最终回复必须保持用户要求的固定格式，不要追加 `自审结果`、说明文字或额外建议段落。
4. 不要为了输出建议而破坏 JSON、补丁或纯代码格式。

## 示例 9：用户要求执行上一轮自审建议

用户说：执行下一步，验证原型图完整性、样式一致性和 PRD 是否同步。

正确做法：

1. 先把这句话识别为“执行上一轮自审建议”，而不是继续解释建议。
2. 实际打开、检查、核对相关文件或页面，收集真实验证依据。
3. 明确区分哪些项目已经验证，哪些还没有验证，哪些因为工具限制暂时无法验证。
4. 完成验证后，再基于最新结果做一轮新的自审，判断是否还存在高优先级缺口。
5. 如果当前已验证范围内没有明显问题，就说明可以进入下一步；如果仍有缺口，就给出新的下一步建议。

## 示例 10：大体量 UI 重构后的抽样自审

用户说：把这 15 页都换成清新自然风，按这个风格重新来。

正确做法：

1. 这类“重做 / 改版 / 换风格”任务即使没有出现“优化/完善”等关键词，也默认属于本 skill 的触发范围。
2. 先完成当前 UI 重构任务。
3. 如果产出体量很大，可采用抽样自审：先检查公共样式、主题变量、页面首尾结构，再抽取 2-3 个代表性页面做重点检查。
4. 自审时优先排查症状级问题，例如页面边界溢出、底部异常空白、固定元素遮挡、同类组件样式不一致、旧风格残留。
5. 输出结论时明确说明本次审查范围；如果只是抽样检查，不要把结论写成“已全量验证”。

## 示例 11：首版创建任务也要自审

用户说：先写一版登录模块 PRD，再补一个首版页面原型。

正确做法：

1. 这类“先做一版 / 先起一个 / 先搭出来”的首版创建任务，也属于本 skill 的默认触发范围。
2. 先完成当前 PRD 和原型的首版产出。
3. 再从产品 / 需求视角和设计 / 前端 UI 视角做自审，检查闭环、异常流程、页面入口出口、关键状态是否缺失。
4. 因为本轮同时改了 PRD 和原型，还要检查名称、页面数量、流程步骤、版本范围是否同步。

## 示例 12：多交付物联动检查

用户说：我把 PRD、原型和页面实现都补完了，你看看还能不能进入联调。

正确做法：

1. 不要只检查页面实现本身，还要把 PRD、原型、页面实现当成联动交付一起检查。
2. 优先核对名称、数量、路径、状态、版本范围是否一致。
3. 如果页面已经做完，但 PRD 页面数没同步、原型路径还指向旧文件、提测状态写错，就应先指出这些同步缺口。
4. 只有在多交付物之间基本对齐后，才可以给出“可以进入联调”的结论。

## 示例 13：验证不足时明确说明缺口

用户说：帮我检查这个页面改动现在能不能说明已经验证通过。

正确做法：

1. 先区分自己当前拿到的证据类型，例如只做了静态检查，还是已经实际运行、打开页面、做过交互验证。
2. 如果当前只能阅读代码或文档，无法运行项目、无法打开页面或缺少必要上下文，就不要直接给出“已验证通过”的结论。
3. 应明确说明当前为什么还不能下高置信度判断，例如“目前只完成了静态检查，未实际打开页面验证渲染和交互，也没有运行结果或测试输出支撑”。
4. 如果合适，再补一条下一步建议，例如“建议补充浏览器检查或运行结果后，再判断是否可视为通过验证”。
