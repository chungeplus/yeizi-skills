# 生成场景规则

根据管理员显式提供的一条 prototype 路径，把已确认 prototype 整理成当前业务场景的 final `scene-rules`。

这个 skill 只做一件事：
- 基于输入 prototype，生成当前 scene-rules

## 核心输入

必填输入只有：
- `一条 prototype 文件路径`

输入约定：
- prototype 路径是管理员已经确认好的输入参数
- `scene-id` 按 prototype 文件名去掉 `-prototype.md` 推导
- 最终输出路径按 `rules/scenes/<scene-id>-rules.md` 生成

## 内置 rules 写法规则

下面这些规则直接作为当前 skill 的内置生成规则使用：

- 规则先给人看：规则文件默认面向人类阅读和修改，文字直接易懂，不写成只方便生成的压缩表达。
- 标题短且语义化：标题直接写约束本身，保持简短，不反复堆来源提示。
- 正文直接且可判对错：正文先写要做什么、保持什么、禁止什么；一条规则只写一个主题，使用可以直接判断对错的表达。
- 说明只保留必要信息：只在影响理解时补来源、说明或示例，不写成长段，不把规则文档写成来源说明或写作教程。
- 人类可见说明默认通俗语义化：涉及管理员或其他人类可见说明时，默认使用通俗、直接、语义化表达，不使用只有 AI 或流程内部才看得懂的术语。

## 最小继续条件

只保留下列会直接影响继续生成的最小检查：

- prototype 路径存在，且能正常读取
- prototype 内容足以整理成当前场景的 rules 文件

不能继续时，只需要直接说明：
- 当前卡在哪里
- 为什么不能继续
- 建议先补什么

不要在这里重做上游流程审核，也不要为了很小概率情况扩写很多分支。

## 整理原则

- 只使用当前 prototype 里的已确认内容整理 final rules
- 目标是当前业务场景的开发规则，不是 prototype 章节直搬
- final 不整理 `场景识别信息`；final 只整理当前 prototype 里的结构规则、技术方案、业务规则和实现边界
- prototype 里已经明确写出的细节内容，不因为“更短”“更整齐”或“更像规则文件”而省掉
- prototype 已经收成目录级、模块级或入口级职责的内容，不重新细化成 prototype 里没有点名的具体业务实现文件
- final 默认按“一条完整判断语义”整理规则，不按“一个事实点”机械切分
- 先看清当前 prototype 每条内容到底表达了几条完整判断语义，再整理 final；final 条目可以多于 prototype 条目，但不能少于 prototype 已经明确写出的规则语义
- 只要一段内容仍然表达同一个判断，就保持在同一条规则里
- 只有拆开后每条仍然独立成立且不改变原意时，才允许拆分
- 切分首先服务于保留规则语义，不服务于减少句长或增加整齐度
- 优先保留 prototype 里带判断条件的规则信息，例如“什么情况下这样做”“只在什么范围内这样做”“满足什么条件时进入某层”
- 共享层、私有层、职责归层、单一事实来源这类判断规则，优先保留“怎么判断”，不要只剩“最后放哪”
- prototype 里已经明确写出的默认依赖方向、默认扩展方向和默认落位倾向，必须保留进 final，不因为“更像规则文件”而省掉
- 允许把 prototype 内容拆成更清晰的规则条目
- 多个动作、多个对象、多个工具、多个文件或多个目录，不自动触发拆分
- 先判断这些内容是否共同组成同一条完整规则；如果是，就保持在同一条规则里
- 只有这些内容拆开后仍然各自独立成立，才拆成多条
- 如果一条规则正文里出现“并”“再”“以及”“和”“与”“同时”等连接词，先判断它们连接的是同一判断里的并列部分，还是可独立成立的多条规则；只有后者才拆开
- 一条规则可以包含必要的条件、范围、例外、顺序和结果，不因为句子稍长、主语重复或并列成分较多就机械拆开
- 下列语义结构默认不能拆坏：条件 + 结果、范围 + 落点、例外 + 主规则、二选一、多选一、条件分支、前后顺序绑定的动作
- 允许把描述句整理成规则句
- 默认一条 prototype 内容只整理成一组紧邻的 final 规则，不跨 prototype 内容吸收别的事实
- 默认不跨 prototype 条目合并；只有两个条目表达的是同一个事实时，才允许合并
- 只在不丢失判断条件、规则价值和规则语义时，合并同主题、同层级、同方向的重复表达
- 允许给规则补简短、语义化标题
- 不为了减少条目数，把多个不同主题硬压成一条长规则
- 不新增 prototype 里没有的业务事实
- 不改变 prototype 已确认的业务含义

## 执行主线

1. 读取 prototype 路径
2. 读取 prototype 内容
3. 推导 `scene-id` 和 final 输出路径
4. 按 rules 写法规则整理成 final `scene-rules`
5. 直接写入 `rules/scenes/<scene-id>-rules.md`
6. 最后统一回报结果

## final 整理要求

- final 默认围绕这些大章节整理：
  - `项目规则`
  - `技术方案`
  - `业务规则`
  - `实现边界`
- final 标题固定整理成 `# <场景标题>场景规则`
- 非目录章节统一整理成 `### <短标题>` + `> <规则正文>`，不在 `###` 下继续堆 bullet
- 非目录章节整理成规则条目，且一条规则只讲一个主题
- final 先覆盖完 prototype 当前内容里的全部规则语义，再考虑条目组织，不先为了收短而压内容
- 判断条件、归层条件和适用范围，只有在它们本身就是一条可独立成立的规则时，才独立成条；如果它们和结果、落点共同组成同一条判断语义，就保留在同一条规则里，不压成笼统结果
- 如果 prototype 某条内容同时包含“适用条件”和“最终落点”，final 必须把这两个信息一起保留下来，不能拆坏它们之间的判断关系
- 如果 prototype 某条内容同时包含多个前后动作，先判断它们是否构成顺序绑定的一条规则；如果是，就保留顺序并保持在同一语义链里
- 如果 prototype 某条内容同时点名多个文件、多个目录、多个职责落点、多个工具、多个校验对象、多个命令、多个模块或多个输出对象，先判断它们是否共同组成同一条完整规则；如果是，就不要为整齐而强拆
- 只有多个文件、多个目录、多个职责落点、多个工具、多个命令或多个模块在拆开后仍然各自独立成立时，才拆成多条并列规则
- 如果 prototype 某条内容已经只锚定到目录、模块、命令入口文件、公开入口或单一事实来源文件，final 保持同级颗粒度，不额外发明更细的业务实现文件名
- 默认不保留 `目录参考`；只有前四章明显不足以表达当前场景结构时，才补一个很轻的目录骨架
- 最终内容要更像当前场景的开发规则文件，而不是 prototype 排版版

## 管理员可见回复

无问题时，最后只回：
- 写入路径
- `scene-id`
- final 标题
- 已完成生成

有问题时，只回：
- 当前哪里有问题
- 为什么不能继续
- 建议先补什么
