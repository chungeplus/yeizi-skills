# 生成场景原型

基于单一参考项目，首次创建 `rules/scenes/prototypes/<scene>-prototype.md`。

这个 skill 只负责生成当前场景的 prototype：

- 不负责生成 final `scene-rules`
- 不负责定义通用项目治理规则
- 不负责修订、重建或回流已有 prototype
- 不把参考项目直接照抄为最终原型，而是在提取后做必要的补充、修正和完善

## 最小安全检查

只保留三条最小安全检查：

- 没有已确认的单一参考项目时，不继续生成；只用人话提醒管理员先补参考项目
- 管理员显式给出的目标路径不在 `rules/scenes/prototypes/` 下，或文件名不符合 `<scene-id>-prototype.md` 时，不继续生成；只用人话提示管理员修正路径
- 最终目标 prototype 路径已存在时，不继续覆盖；直接提示切换到 `revise-scene-prototype`

目标 prototype 已存在时，固定回包：
`目标 prototype 已存在，这次应改走 /revise-scene-prototype。本次没有继续提取，也没有写文件。`

缺少参考项目时，固定回包：
`这次生成需要先确认 1 个参考项目。我还没有继续提取，也没有写文件。`

目标路径不符合约束时，固定回包：
`目标路径需要写到 rules/scenes/prototypes/<scene-id>-prototype.md。我这次还没有继续提取，也没有写文件。`

## skill 目标

- 以单一参考项目为主驱动，提取并整理出一份严谨、场景固定的 prototype
- 把当前 skill 固定为“主场景原型提取器”，不负责通用场景意图识别，也不负责从输入里猜多个候选场景
- 保留真实、稳定、场景相关的项目细节，不把原型抽空成虚泛通用规则
- 把参考项目作为主上下文，把外部证据只当补证据来源，不反过来改写参考项目的主结构、主风格和主技术结论
- 默认由 AI 先完成提取、归类、补充、修正、完善和自审；只有出现待管理员决策的问题时，才发起管理员交互；只有少量高影响问题才额外插入第 `3` 轮疑难点确认

## 核心输入

必填输入只有：

- `单一参考项目`

可选输入：

- 目标 prototype 路径
- 当前工作区里的现有项目上下文
- 管理员另行提供的项目初始基线或补充约束

输入处理原则：

- 一个参考项目只对应一个场景，不拆多个候选 scene
- 当前 skill 的职责是围绕这个主场景整理固定业务场景原型，不向“更通用的场景定义”外扩
- 默认只围绕参考项目的主场景写，不展开次级使用形态；README、`package.json` 或代码里即使明显存在 module usage 等副用法，也只在管理员明确要求时才展开
- 默认读取整个参考项目，不要求管理员指定“提取哪一部分”
- 如果管理员没有提供目标路径，由 AI 根据参考项目的核心场景自行命名文件，并固定写入 `rules/scenes/prototypes/`
- 如果管理员显式给出目标路径，必须同时满足：
  - 位于 `rules/scenes/prototypes/`
  - 文件名符合 `<scene-id>-prototype.md`
  - 不满足时直接停止，并提示管理员修正路径
- 自行命名时，scene id 必须保持 `lowercase kebab-case`
- 自行命名固定按这条顺序执行：先提取主场景标题，再把标题归一化成稳定 `scene-id`，最后由 `scene-id` 生成 `<scene-id>-prototype.md`
- 归一化阶段禁止同义词自由漂移；同一类主场景必须收敛到同一套固定说法，例如“依赖升级”和“包依赖升级”要统一收成同一套标题与 `scene-id`
- scene id 只描述业务场景本身，不额外带 `scene`、`rules`、技术名、工具名或参考项目产品名
- 最终文件名固定为 `<scene-id>-prototype.md`
- 最终写入的 prototype 不区分“项目提取内容”和“AI 补充内容”；一旦确认并落盘，就全部视为正式内容
- 默认由参考项目主导场景结构、技术结论和命名收敛
- 当前项目上下文和外部证据只做补充，不改写参考项目的主结构、主风格和主技术结论
- 如果管理员显式给出的补充约束与参考项目冲突，停止当前自动收敛，指出冲突并请管理员拍板
- 抽象职责基线只做内部归类辅助，不单独产出结构答案

## 内部参考

只在需要时读取下面 3 份内部 reference：

- `references/project-baseline-responsibilities.md`
  - 用于内部判断内容属于什么角色、是否需要提升、哪些角色只能全局存在
  - 不把这里的抽象角色词原样暴露给管理员
- `references/edge-cases.md`
  - 只在边界判断确实卡住时读取
  - 这里只放案例化解释，不覆盖 `SKILL.md` 和 `references/prototype-contract.md` 里的落盘硬规则
- `references/prototype-contract.md`
  - 用于固定章节、章节职责和 `generic / concrete` 抽象层级约束

## 执行主线

整个流程按下面 8 步执行：

1. `确认参考项目与目标路径`
   - 确认当前 run 已有单一参考项目
   - 如果管理员显式给了目标路径，先校验它是否位于 `rules/scenes/prototypes/` 下，且文件名符合 `<scene-id>-prototype.md`
   - 如果管理员显式给的目标路径不满足上面两条，立即停止并提示管理员修正路径
   - 如果管理员显式给了目标路径且校验通过，就以该路径为准
   - 如果管理员没给目标路径，就先提取主场景标题，再按固定归一化规则生成稳定 `scene-id`，最后推定 `<scene-id>-prototype.md` 并写入 `rules/scenes/prototypes/`
   - 如果最终目标路径已存在，立即停止并重定向到 `revise-scene-prototype`

2. `读取整个参考项目`
   - 阅读项目 README、配置文件、依赖清单、入口文件、主目录树和关键流程文件
   - 提取项目的整体用途、主交互方式、主技术、共享/私有组织方式、运行流程和关键模块职责
   - 如果参考项目不仅给出了目录结果，还给出了稳定的代码落点判断，先提取“什么情况下放哪”，再整理最终目录和文件落点
   - 默认把整个项目视为同一个主场景的上下文，不再拆多个候选 scene，也不默认展开次级使用形态

3. `内部归类与提取`
   - 结合 `references/project-baseline-responsibilities.md` 做内部角色归类、提升和边界判断
   - 从真实项目里提取：
     - 目录结构和主入口
     - 共享层与私有层的组织方式
     - 默认依赖方向和默认扩展方向
     - 运行时校验、配置、错误、业务、工具、服务访问和状态能力的落点
     - 各类代码内容在什么情况下进入共享层、什么情况下留在局部、什么情况下保留当前文件
     - 真实存在的输入来源、确认点、副作用、输出方式和错误回报方式
   - 保留真实、稳定、场景固定的项目细节，不因为“太具体”就把内容抽空
   - 不要只因为已经能看到 `config / constants / tools / types / schemas` 这些目录，就把场景规则写成目录清单
   - 如果某些内容暂时无法稳定归类，允许把它们短暂留在内部 `未归类内容` 集合里，但这一状态不得直接进入最终 prototype

4. `补充、修正与自审`
   - 先用参考项目完成大部分内容提取
   - 只有当参考项目不能稳定支撑某段章节内容时，才补充开源项目、官方文档或联网证据
   - 外部证据只用于补足缺口，不用于改写参考项目的主结构、主风格和主技术结论
   - 小的业务场景细节、单文件真实职责细节、局部但稳定的流程细节，不是噪音；只要真实、稳定、场景相关，就应该进入 prototype
   - 只有“缺少当前项目 / 参考项目 / 管理员支撑，只是外部证据补出来的候选内容”才算噪音；这类内容允许被 AI 直接丢弃
   - 参考项目名字、样本仓库名、实现载体名这类专有词，只有在它们本身就是当前主场景的业务事实时才允许进入最终 prototype；如果它们只是参考项目身份，就要抽成业务角色表达，例如远端仓库、远端技能索引或远端技能文件来源
   - 如果参考项目不足以支撑关键结论，而该结论会影响章节内容、目录边界或最终命名，把它视为低频疑难点；不要用抽象职责基线替它补模板
   - AI 自审以下问题：
     - 有没有误提取、误归类、误抽象
     - 有没有把噪音、临时痕迹或无证据脑补写成正式内容
     - 有没有把样本项目名误写成当前场景的业务事实
     - 有没有把 `场景结构规则` 和 `实现边界` 写混
     - 有没有把“什么情况下放哪”的判断压成只剩目录结果或文件结果
     - 有没有出现空泛、谁都能套的句子

5. `需要时再给管理员轻摘要`
   - 第一轮对外消息只回答 4 件事：
     - 我从参考项目里提取到的场景是什么
     - 当前状态是什么
     - 当前是否存在问题；如果有，问题是什么
     - 我的建议是什么
   - 只有当前确实存在待管理员决策的问题时，才发出这一轮消息；如果 AI 已经判断当前没有问题，就不发起这一轮交互，直接继续执行下面的 skill 内容
   - 不解释 skill 内部流程，不外露抽象角色词，不逐章展开重内容，也不默认返回完整 prototype 正文
   - 一旦发起这一轮，管理员先看到的是轻摘要、状态和建议，不是完整 `6` 章草稿

6. `升级高影响疑难点`
   - AI 能稳定判断的内容，默认自己处理；这一分支只决定是否需要额外插入第 `3` 轮低频疑难点确认
   - 只有在会影响下面这些结论时，才视为高影响疑难点：
     - `6` 章内容里的主结论
     - 目录/模块边界
     - 主技术结论
     - 业务主流程
     - 最终落盘内容
   - 高影响疑难点先由 AI 自己复核
   - AI 自己仍不稳时，可以先走多智能体讨论
   - 只有多智能体仍然不能稳定收敛时，才在两轮主流程之间额外插入第 `3` 轮，把问题打包给管理员
   - 这类第 `3` 轮一次最多打包 `2-3` 个强相关疑难点，并为每个点给出明确建议

7. `整理完整原型`
   - 只有当当前内容已经全部收口到这三种状态之一时，才进入完整原型整理：
     - 已确认为噪音并丢弃
     - 已完成稳定归类
     - 已升级给管理员且相关疑难点已清
   - 不允许把 `未归类内容`、`待定项` 或临时补充段直接带入最终 prototype
   - 在项目提取、补充和管理员必要决策收口后，整理完整的 `6` 章 prototype
   - 章节结构、章节职责和 `generic / concrete` 约束只按 `references/prototype-contract.md` 执行
   - 参考项目已经给出稳定目录名和文件名时，默认输出 concrete 内容
   - 只有项目确实没有给出稳定名称时，才允许局部保留最小角色语义占位
   - concrete 原型默认统一采用当前参考项目里最稳定的一套真实命名；如果参考项目没有显式采用混用写法，不要在同一份 concrete prototype 里混用多套同义目录名
   - prototype 默认只固定到目录层级、出入口文件和极少数单一事实来源文件；不默认钉死具体业务实现文件名
   - 只有启动入口、程序主入口、根注册入口、命令入口文件、公开入口或单一事实来源文件，才允许写成具体文件名
   - 整理完整 draft 前先做一轮章内自检：
     - 凡是回答“怎么组织、怎么分层、怎么分布、怎么复用、谁是单一事实来源”的句子，只写进 `场景结构规则`
     - 凡是回答“哪个文件、目录或模块负责什么”的句子，只写进 `实现边界`
     - 凡是同时包含两种语义的句子，先拆句再归章
     - 如果当前原型只写出了“最后放在哪”，但没有保留参考项目里已经稳定存在的共享/私有、局部/共享、命令层/能力层判断，视为提取不完整，不继续落盘
     - 如果当前原型把多条判断规则压成单条结果摘要，先拆开再落盘
     - 如果 `实现边界` 写到了 parser、formatter、builder、comparator、installer 这类具体业务实现文件名，且它们既不是出入口文件、命令入口文件也不是单一事实来源文件，先回退成目录或模块级职责表达再落盘

8. `最终审核与落盘`
   - 最后一轮对外消息只回答：
      - 当前是否已无问题；如果还有问题，问题在哪
      - 建议怎么处理
      - `scene-id`
      - 最终目标路径
      - 当前是否可以写入，或已经写入
   - 默认不展示完整 `6` 章 draft；只有管理员明确要求查看当前产物内容时，才额外展示完整 draft
   - 只有这一轮仍然存在问题、冲突或待拍板事项时，才发出这一轮消息并等待管理员决定是否继续
   - 如果 AI 已经判断当前无问题且可以写入，就直接把 prototype 写入最终路径，不额外发起确认
   - 写入成功后的最终对外消息统一回报结果，且必须明确包含 `已写入`、`已落盘` 或同等完成信号

## 章节生成原则

固定 `6` 章继续保留，但驱动方式改为“参考项目提取 + AI 整理”：

- `场景识别信息`
  - 主要来自项目的整体用途、主交互形态、入口和主技术轮廓
  - 回答“这个项目对应的场景是什么”
- `场景结构规则`
  - 主要来自真实目录、共享/私有组织方式、提升路径、代码落点判断和单一事实来源
  - 可以补少量默认倾向，例如哪一层默认依赖哪一层、什么情况下优先继续写原文件或现有模块
  - 回答“这个场景在当前项目里怎么组织”
- `技术方案`
  - 主要来自依赖、配置、入口和真实技术使用情况
  - 回答“这个场景实际采用什么技术”
- `业务规则`
  - 主要来自真实流程、交互步骤、确认点、副作用和输出/报错方式
  - 回答“这个场景运行时怎么工作”
- `实现边界`
  - 主要来自真实文件、目录、模块的职责划分
  - 回答“哪些位置各自负责什么”
  - 默认只细到目录、模块、出入口文件和极少数单一事实来源文件，不默认点名具体业务实现文件
- `目录参考`
  - 主要来自参考项目的主干目录结构
  - 默认只保留支撑主场景运行的生产主干目录和少量关键入口，不机械打印全仓库，也不顺手列出一串具体业务实现文件
  - `test/`、`.github/`、文档目录、发布辅助目录这类内容，只有当前主场景本身就是测试、发布或文档场景时才进入目录树

## 管理员可见回复规则

管理员是人类，回复必须通俗、清晰、可直接决策。

对外只展示：

- 我提取到的结果
- 当前状态
- 当前是否存在问题；如果有，问题是什么
- 我的建议
- 现在需要管理员决定什么（如果当前确实有待拍板问题）
- 当前是否可以继续

对外不要展示：

- `scope guard`
- `项目初始基线` / `职责基线`
- `已知事实 / 未知事实 / 待决项`
- `AI 自审`
- `多智能体讨论`
- 任何内部执行步骤、内部推理顺序或抽象角色词

管理员可见轮次目标：

- 正常 run：`0-2` 轮
- 复杂 run：最多 `3` 轮
- 如果整个流程里没有待管理员决策的问题，管理员可见交互可以为 `0` 轮；AI 直接执行并在最后统一回报结果
- 第 `1` 轮只在当前确实存在待管理员决策的问题时才出现；它负责给管理员看轻摘要和建议，不默认出现
- 第 `2` 轮只在最终落盘前仍有问题时才出现；如果 AI 此时已判断无问题且可以写入，就直接执行写入并回报结果
- 只有管理员明确要求查看当前产物内容时，才额外展示完整 `6` 章 draft

超过 `3` 轮，说明当前输入质量不足，不属于正常主流程。

## 护栏

- 不生成 final `scene-rules`
- 不把 prototype 写成通用项目治理规则副本
- 不把参考项目拆成多个场景候选
- 不要求管理员先写长篇场景介绍
- 不要求管理员参与角色归类、目录提升或章节内部分布判断
- 不暴露内部流程词、内部 reference 名称或内部执行细节
- 不把抽象角色规则直接写成最终 prototype 的目录答案
- 不把“什么情况下放哪”的判断压缩成只剩目录结果
- 不把 `references/project-baseline-responsibilities.md` 里的命名例子当默认模板套用到所有项目
- 不因为内容具体就把它抽空成虚泛规则
- 不把开源项目 / 联网证据写成主驱动源
- 不把抽象职责基线当成薄参考项目时的模板补位来源
- 不在无证据时凭空补齐看起来完整的一整套章节
- 不在同一份 concrete prototype 里混用参考项目未明确采用的多套同义目录命名
