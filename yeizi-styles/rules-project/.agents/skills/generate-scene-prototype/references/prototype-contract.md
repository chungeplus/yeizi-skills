# Scene Prototype 输出契约

这是 scene prototype 的共享输出契约真源。
只定义最终 prototype 的固定章节、章节职责和产物层抽象约束，不定义首次生成或修订 workflow。

## 固定章节

写入 `rules/scenes/prototypes/<scene>-prototype.md` 时，固定使用下面结构：

```md
# <场景标题>场景原型
## 场景识别信息
## 场景结构规则
## 技术方案
## 业务规则
## 实现边界
## 目录参考
```

顶层命名固定遵守下面约束：

- `<scene>` 只描述业务场景本身，默认使用稳定的 `lowercase kebab-case`
- `<场景标题>` 只描述业务场景本身，不额外带 `scene`、`rules`、技术名、工具名、参考项目产品名或样本仓库名
- 只有当某个专有名词本身就是当前主场景的业务事实时，才允许进入标题或 `<scene>`
- 最终文件名固定为 `<scene>-prototype.md`

## 章节职责

- `场景识别信息`
  - 回答：当前参考项目对应的场景是什么，它的主交互形态和主技术轮廓是什么
  - 只保留场景身份、业务形态和少量主技术信号
  - 默认控制在 `1-2` 条
  - 参考项目名字、样本仓库名和实现载体名只有在它们本身就是当前主场景的业务事实时才允许保留；否则优先抽成业务角色表达
  - 不展开目录树、执行骨架、辅助库清单、校验规则或构建工具名单
- `场景结构规则`
  - 回答：这个场景在当前项目里怎么组织、怎么分布、怎么提升、谁是单一事实来源
  - 只承载当前项目里真实存在的结构规律
  - 可以出现 concrete 目录名，但前提是它们确实表达结构分布、提升路径或单一事实来源
  - 如果当前场景存在稳定的共享/私有、局部/共享、命令层/能力层落点判断，必须写出“什么情况下放哪”，不能只写最终目录名或最终落点结果
  - 如果某类代码内容同时有“适用条件”和“最终落点”，优先同时保留这两层信息，不只保留结果
  - 不重复场景介绍，也不散落技术清单
- `技术方案`
  - 回答：当前场景采用什么运行时、语言、框架、运行时校验、交互方式、构建工具和代码校验规则
  - 具体库名和具体工具链统一落在这里
- `业务规则`
  - 回答：运行时如何收集输入、做校验、要求确认、触发副作用、返回结果和报告失败
  - 只写稳定、真实、场景固定的业务行为
  - 不把样本项目名直接写成业务角色，优先写远端仓库、远端索引、远端文件来源这类场景角色表达
- `实现边界`
  - 回答：某个文件、目录、模块各自负责什么
  - 每条都优先锚定到明确的目录、模块、出入口文件或单一事实来源文件，再说明职责
  - 默认不点名具体业务实现文件；只有启动入口、程序主入口、根注册入口、命令入口文件、公开入口或单一事实来源文件，才允许写成具体文件名
  - 优先使用正向职责表达；只有正向表达不足以防歧义时，再补必要的反向限制
  - 只写当前项目里具体哪个位置负责什么，不吞掉本来属于“怎么判断该放哪”的规则
  - 不把“怎么组织”写回这一章；结构分布语义留在 `场景结构规则`
- `目录参考`
  - 只承载目录树表达，不新增规则语义
  - 只能保留一个 `text` 代码块目录树
  - 默认保留支撑主场景运行的生产主干目录和少量关键入口，不机械打印整个仓库，也不默认列出一串具体业务实现文件
  - `test/`、`.github/`、文档目录、发布辅助目录这类内容，只有当前主场景本身就是测试、发布或文档场景时才允许进入目录树

最终 prototype 只允许这 `6` 个固定章节承载正文内容，不允许额外追加：

- `待定项`
- `未归类项`
- `临时补充段`
- 其他不属于固定章节的正文段落

## generic / concrete 产物约束

- `concrete`
  - 参考项目已经给出稳定目录名、文件名、入口名或模块名时，默认输出 concrete 内容
  - concrete 产物优先写当前项目真实存在的名称，不回退成抽象占位
  - 如果当前参考项目没有显式采用混用写法，同一份 concrete prototype 不要混用多套同义目录名、入口名或模块名
- `generic`
  - 只有项目确实没有给出稳定名称时，才允许局部保留 generic 表达
  - generic 只用于局部缺名位置，不作为整份原型的默认状态
  - generic 占位应使用最小角色语义表达，并在相邻文字里说明该 concrete 名称当前尚未稳定

generic / concrete 只表示抽象层级，不承载具体场景模板、默认目录答案或固定项目脚手架。

## 结构与边界的固定要求

- 只要当前场景已确认存在多个私有模块，或这些私有模块之间会发生能力复用，`场景结构规则` 就必须显式写出：
  - 不直接引入对方私有内容
  - 只通过公开入口读取私有能力
- `场景结构规则` 负责回答“怎么组织”
- `实现边界` 负责回答“各位置做什么”
- 一条内容如果同时包含两种语义，先拆句再归章
