# 目录职责与提升规则真源

这是 `revise-scene-prototype` 的内部职责 reference。
只在需要判断“修订内容怎么归类、怎么分布、怎么提升、哪些角色只能全局存在”时读取本文件。
它服务 AI 内部修订判断，不是管理员需要理解的对外流程词。

如果管理员显式给出补充约束、项目事实或参考事实，把它们当成补充证据使用；不要把本文件整包导入当前 scene，只选择与当前 prototype 及补充事实稳定匹配的规则。
本文件只帮助 AI 做内部角色判断，不负责重新从参考项目提取一版新结构，也不在证据不足时凭空补全当前 prototype 未支撑的 concrete 结构。

## 内容先归类

- 新增或修订内容前，先判断它是类型、运行时校验、配置、错误、常量、业务代码、工具代码、服务访问能力还是状态能力，再决定它该落在哪一类角色。
- 不因为调用位置、文件来源、实现方式或样例项目恰好这么写，就把内容放进错误角色。
- 如果当前内容暂时不属于这 `9` 类，先暂列为未归类内容，等 prototype 现有证据、管理员补充事实或明确决策补足后再归类。
- `未归类内容` 只允许作为内部中间态存在，不得直接进入最终 prototype；在落盘前，它必须被归类、被确认为噪音并丢弃，或升级成疑难点。

## 内容类型规则

- 类型内容：
  - 接口、类型别名、对象式枚举和类型工具都属于类型内容
  - 只服务 `1` 个私有模块 -> 归入该模块的私有类型角色
  - 被 `2` 个以上私有模块共享 -> 归入共享类型角色
- 运行时校验内容：
  - 运行时校验结构、校验规则和 `zod` schema 都属于运行时校验内容
  - 只服务 `1` 个私有模块 -> 归入该模块的私有校验角色
  - 被 `2` 个以上私有模块共享 -> 归入共享校验角色
- 常量内容：
  - 只在 `1` 个文件使用 -> 留在当前文件
  - 被同模块 `2` 个以上文件共享 -> 归入模块内共享常量角色
  - 被 `2` 个以上私有模块共享 -> 归入共享常量角色
  - 对象式枚举属于类型内容，不归入常量角色
- 配置内容：
  - 会随着项目设定、模块设定或环境设定调整 -> 归入共享配置角色
  - 不建立私有配置角色
- 错误内容：
  - 错误类、错误码、错误标题、错误映射和错误处理相关内容 -> 归入共享错误角色
  - 不建立私有错误角色
- 业务代码：
  - 只服务 `1` 个私有模块 -> 留在该模块内部
  - 被 `2` 个以上私有模块共享 -> 归入共享业务角色
  - 即使未达到 `2` 个以上私有模块，只要它直接承载项目入口到多个关键流程之间的业务编排，且离开当前项目就说不通 -> 也归入共享业务角色
  - 只是在入口文件里被顺手调用一次，或只替单个流程做局部拼装，不算共享业务角色触发条件
- 工具代码：
  - 只服务 `1` 个私有模块 -> 留在该模块内部
  - 被 `2` 个以上私有模块共享 -> 归入共享工具角色
  - 不因为“服务项目入口和整个项目流程”就自动提升到共享工具角色
- 服务访问能力：
  - 面向外部接口、仓储、SDK、请求客户端或远端资源访问的能力，属于服务访问能力
  - 主要在解决“怎么访问外部能力、怎么发请求、怎么读写远端或持久化资源”的内容，归入服务访问能力
  - 即使服务访问能力被业务流程调用，也不因此自动变成共享业务角色
  - 如果某段内容主要在做业务编排、流程决策、条件分支、确认步骤或多步组合，即使它内部调用了外部接口，也仍然优先归入业务代码，而不是服务访问能力
  - 默认归入共享服务访问角色
  - 不建立私有服务访问角色
- 状态能力：
  - 被项目主动维护、可被读取/更新、会跨流程或跨交互持续存在的状态容器或状态模型，才属于状态能力
  - 普通局部变量、一次性中间值、单函数内临时缓存不属于状态能力
  - 默认归入共享状态角色
  - 不建立私有状态角色

## 分布规则

- 入口层只负责装配，不负责主要业务流程
- 私有模块按当前项目里的业务名称组织，不在通用 reference 里写死具体模块名
- 共享层与私有层分开
- 共享层不承载只服务 `1` 个私有模块的私有逻辑
- 私有内容留在对应模块内部
- 其他模块如果需要对应能力，只通过对方公开入口读取，不直接引入别的模块私有内容
- 只服务 `1` 个私有模块的业务函数、工具函数、类和流程文件，留在该模块内部
- 业务代码可以依赖服务访问能力，但服务访问能力不承载项目级业务编排

## 提升规则

- 单文件使用的固定常量 -> 留在当前文件
- 被同模块 `2` 个以上文件共享的常量 -> 提升到模块内共享常量角色
- 被 `2` 个以上私有模块共享的常量 -> 提升到共享常量角色
- 被 `2` 个以上私有模块共享的类型内容 -> 提升到共享类型角色
- 被 `2` 个以上私有模块共享的运行时校验内容 -> 提升到共享校验角色
- 被 `2` 个以上私有模块共享的业务代码 -> 提升到共享业务角色
- 只要业务代码直接承载项目入口到多个关键流程之间的业务编排，且离开当前项目就说不通 -> 即使未达到 `2` 个以上私有模块，也提升到共享业务角色
- 只在入口文件里被调用一次、但没有承载多个关键流程之间业务编排的内容 -> 仍然留在当前私有模块，不提升到共享业务角色
- 被 `2` 个以上私有模块共享的工具代码 -> 提升到共享工具角色
- 配置内容、错误内容、服务访问能力和状态能力默认直接落到共享角色，不先在私有层中转

## 存在性约束

- 共享配置角色默认只有一套，不建立私有配置角色
- 共享错误角色默认只有一套，不建立私有错误角色
- 共享服务访问角色默认只有一套，不建立私有服务访问角色
- 共享状态角色默认只有一套，不建立私有状态角色
- 私有模块不得复制共享配置角色、共享错误角色、共享业务角色、共享工具角色、共享服务访问角色、共享状态角色
- 私有模块默认可承载这些私有角色：私有类型角色、私有校验角色、模块内共享常量角色、只服务当前模块的私有业务职责、只服务当前模块的私有工具职责
- 如果当前场景确实需要突破这些约束，必须在当前场景原型里显式写出，不能因为样例项目恰好存在就自动沿用

## 命名映射参考

上面的规则先决定“内容该归哪一类角色、什么时候提升、哪些角色只能全局存在”，并不直接规定目录名。
最终 prototype 优先写当前 prototype 对应项目里已经稳定的真实目录名和真实文件名，不把下面的例子当成默认答案。

常见但非强制的映射例子：

- 共享类型角色 -> `types/`
- 共享配置角色 -> `config/`
- 共享校验角色 -> `schemas/`
- 共享常量角色 -> `constants/`
- 共享错误角色 -> `errors/`
- 共享业务角色 -> `features/`
- 共享工具角色 -> `tools/`
- 共享服务访问角色 -> `services/`
- 共享状态角色 -> `store/`
- 私有类型角色 -> 私有模块下的 `types/`
- 私有校验角色 -> 私有模块下的 `schemas/`
- 模块内共享常量角色 -> 私有模块下的 `constants/`

如果当前 prototype 对应项目最终选择某个目录名来承载某种角色，就把该角色的存在性约束一并带上。例如：

- 如果共享配置角色映射成 `config/`，那当前项目只保留 `1` 个全局 `config/`
- 如果共享常量角色映射成 `constants/`，那被 `2` 个以上私有模块共享的常量都收敛到这一层
- 如果模块内共享常量角色映射成私有 `constants/`，那它只服务当前模块，不自动升级为全局共享层
