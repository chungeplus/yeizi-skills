# TypeScript `directory-rules` 辅助内容集中化设计

## 目标

把 `TypeScript` 项目里的辅助内容目录规则重构成一套更偏“人读功能代码优先”的结构。

这套结构只处理目录规则本身，不处理具体实现写法。

本次设计要同时满足下面 4 个目标：

- 功能目录优先保留功能逻辑，减少人阅读时被配套辅助目录打断。
- 类型和校验集中管理，降低 AI 生成代码时的落点歧义。
- `config/` 和 `constants/` 的语义边界保持清晰。
- 规则条目继续满足“单条只约束一件事、直接可判对错、有限且准确”。

## 本次范围

本次只重构 `rules/technologies/typescript/directory-rules.md` 的目录规则设计。

本次处理下面内容：

- 内容定义怎么写
- 内容落地规则怎么写
- 目录名称规则怎么写
- 类型、校验、常量、配置的目录边界怎么收紧

本次不处理下面内容：

- 不改 `code-rules.md`、`shared-rules.md` 的项目级通用原则
- 不改 `implementation-rules.md` 的具体实现写法
- 不约束 `src/`、`commands/` 等实际私有业务目录里的实现组织

## 核心决策

采用“功能逻辑前置，辅助内容后置，全局集中，路径镜像”的目录设计。

这组决策固定为：

- 功能目录不建立配套的 `types/`、`schemas/`、`constants/` 子目录。
- 类型内容统一放到全局 `types/`。
- 校验内容统一放到全局 `schemas/`。
- 类型文件和校验文件按对应源文件路径做镜像落位。
- 单文件使用的固定值留在当前文件。
- 只要固定值被多个文件复用，就直接提升到全局 `constants/`。
- `config/` 只放可调整、可配置的项目设定。
- `constants/` 只放共享固定值，不混入可调配置。
- 不再建立模块内 `types/`、`schemas/`、`constants/`。

## 为什么采用这套方案

这次设计不是为了让内容分类看起来更“纯”，而是为了让人阅读项目时先看到功能逻辑，再按需查看辅助内容。

保留模块内 `types/`、`schemas/`、`constants/` 的做法，虽然语义自然，但会让阅读功能代码的人频繁在功能目录和辅助目录之间来回切换。

把类型和校验收拢到全局镜像目录后：

- 人可以先只看功能目录
- AI 仍然能靠镜像路径稳定找到对应辅助内容
- 目录规则不再要求反复判断“当前文件 / 模块内 / 全局共享”三层落点

保留全局 `constants/` 而不并入 `config/`，是为了维持两个目录的稳定边界：

- `config/` 表示可调整、可配置的项目设定
- `constants/` 表示共享固定值

## 规则结构

新的 `directory-rules.md` 固定为 3 个章节：

1. 内容定义
2. 内容落地规则
3. 目录名称规则

每个章节只回答一类问题：

- 内容定义只回答“这类内容是什么”
- 内容落地规则只回答“这类内容放哪里”
- 目录名称规则只回答“这类内容对应什么目录名”

不在同一条规则里同时写定义、落地和命名。

## 内容定义设计

### 类型内容

`interface`、`type` 和对象式枚举属于类型内容。

### 校验内容

使用 `Zod` 编写的 schema 和由 schema 组合出的校验结构属于校验内容。

### 常量内容

固定值属于常量内容。

### 配置内容

可调整、可配置的项目设定属于配置内容。

### 错误内容

错误相关内容属于错误内容。

### 共享功能代码

被多个模块复用且仍承载业务语义的功能文件或目录模块属于共享功能代码。

### 共享工具代码

被多个模块复用且不承载业务判断的通用函数或目录模块属于共享工具代码。

### 请求内容

调用请求客户端的请求函数、请求地址封装和请求适配结构属于请求内容。

### 状态内容

状态容器、状态模型和状态读写结构属于状态内容。

### 测试内容

为 `TypeScript` 源文件服务的测试代码属于测试内容。

## 内容落地规则设计

### 类型落地规则

- 类型内容统一放到全局 `types/`。
- 类型文件按对应源文件路径做镜像落位。
- 镜像类型文件只服务对应的源文件或对应的目录模块。

### 校验落地规则

- 校验内容统一放到全局 `schemas/`。
- 校验文件按对应源文件路径做镜像落位。
- 镜像校验文件只服务对应的源文件或对应的目录模块。

### 常量落地规则

- 单文件使用的固定值留在当前文件。
- 被多个文件复用的固定值提升到全局 `constants/`。

### 配置落地规则

- 配置内容放到全局 `config/`。

### 错误落地规则

- 错误相关内容放到全局 `errors/`。

### 共享功能代码落地规则

- 被多个模块复用且仍承载业务语义的代码放到共享功能目录。
- 一个共享功能需要多个文件时，使用共享功能目录模块承载。

### 共享工具代码落地规则

- 被多个模块复用且不承载业务判断的代码放到共享工具目录。

### 请求内容落地规则

- 通用请求客户端和请求传输层代码放到 `service/request/`。
- 按外部资源组织的请求函数和请求地址封装放到 `service/apis/`。

### 状态内容落地规则

- 状态内容放到全局 `store/`。

### 测试内容落地规则

- 被测内容的测试跟随被测内容同目录。
- 多个测试共用的辅助内容放到测试子目录。

## 目录名称规则设计

### 类型目录使用 `types/`

全局类型目录统一使用 `types/`。

### 校验目录使用 `schemas/`

全局校验目录统一使用 `schemas/`。

### 常量目录使用 `constants/`

全局共享常量目录统一使用 `constants/`。

### 配置目录使用 `config/`

全局配置目录统一使用 `config/`。

### 错误目录使用 `errors/`

全局错误目录统一使用 `errors/`。

### 功能目录使用 `features/`

共享功能目录统一使用 `features/`。

### 工具目录使用 `tools/`

共享工具目录统一使用 `tools/`。

### 请求根目录使用 `service/`

共享请求根目录统一使用 `service/`。

### 请求资源目录使用 `service/apis/`

按外部资源组织的请求目录统一使用 `service/apis/`。

### 请求传输层目录使用 `service/request/`

通用请求传输层目录统一使用 `service/request/`。

### 状态目录使用 `store/`

共享状态目录统一使用 `store/`。

## 示例

如果功能文件是 `features/skill/get-list.ts`，则对应辅助内容按下面方式落位：

- 类型内容 -> `types/features/skill/get-list.ts`
- 校验内容 -> `schemas/features/skill/get-list.ts`
- 只在当前文件使用的固定值 -> 留在 `features/skill/get-list.ts`

如果某个固定名称表、固定路径段或固定标识值被多个文件复用，则提升到全局 `constants/`，不进入 `config/`。

如果某个目录、开关、默认值或运行设定需要调整，则进入全局 `config/`，不进入 `constants/`。

## 取舍

这套方案的主要收益是：

- 功能目录更接近“只看逻辑就能理解主流程”
- `types/` 和 `schemas/` 的落点更稳定
- `config/` 和 `constants/` 的边界更容易判断

这套方案的主要代价是：

- 需要维护类型和校验的镜像路径
- 功能文件移动或重命名时，对应镜像文件也需要同步调整

这个代价是可接受的，因为它换来的是更稳定的人读体验和更稳定的 AI 落点判断。

## 验收标准

当这套设计落到 `directory-rules.md` 时，需要同时满足下面条件：

- 文件固定分为“内容定义 / 内容落地规则 / 目录名称规则”3 个章节
- `directory-rules.md` 不再出现模块内 `types/`、`schemas/`、`constants/` 规则
- 类型内容统一落到全局 `types/`
- 校验内容统一落到全局 `schemas/`
- 被多个文件复用的固定值统一落到全局 `constants/`
- `config/` 只承载可调整、可配置的项目设定
- 镜像类型文件和镜像校验文件都只服务对应源文件或对应目录模块
- 功能目录里不再要求额外建立配套的 `types/`、`schemas/`、`constants/` 子目录
- 规则正文继续保持直接、有限、可判对错
