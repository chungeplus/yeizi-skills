# `code-rules` 写法设计

## 目标

明确 `rules/projects/code-rules.md` 的默认写法边界，让项目级跨语言代码规则和语言级技术规则保持稳定分层。

## 本次范围

本次只处理下面 2 件事：

- 明确 `code-rules.md` 默认写“原则句”，不写推荐/不推荐代码示例
- 确认 `comment-rules.md` 里的“注释直接写清意思”适合迁入 `code-rules.md` 时使用项目级简化写法

本次不处理下面内容：

- 不直接修改 `rules/projects/code-rules.md`
- 不直接修改 `rules/technologies/typescript/comment-rules.md`
- 不在这次把其他注释规则整批迁到项目级

## 结论

`rules/projects/code-rules.md` 默认只写可以直接判断对错的规则正文，不写绑定具体语言的推荐/不推荐代码示例。

## 为什么不保留代码示例

- `code-rules.md` 面向项目级跨语言规则，示例一旦写成代码块，就会默认绑定某种具体语言
- 对项目级规则来说，代码示例更像教学材料，不是必须的规则正文
- 示例保留在 `rules/technologies/*` 更合适，因为语言级文件可以自然使用本语言语法展示推荐写法和不推荐写法

## 文件分工

### `rules/projects/code-rules.md`

默认承接下面这类内容：

- 跨语言成立的代码原则
- 不依赖单一语言语法的注释规则
- 不依赖单一语言语法的日志和错误信息书写规则

默认写法：

- 短标题
- 一句规则正文
- 不带推荐/不推荐代码块

### `rules/technologies/typescript/comment-rules.md`

继续承接下面这类内容：

- 需要用 `TypeScript` 语法举例的注释规则
- 推荐写法 / 不推荐写法示例
- `/** */`、`@param`、`@returns`、`@throws`、`@example` 这类文档风格细则

## “注释直接写清意思”迁入项目级时的写法

当前 `comment-rules.md` 里的这条规则：

### 注释直接写清意思

> 注释直接写清当前内容在做什么、为什么这样做，或会带来什么影响。

适合迁入 `code-rules.md`，但迁入时只保留上面的标题和规则正文，不保留下面这类语言级示例：

- 推荐写法代码块
- 不推荐写法代码块

## 迁入后的项目级形态

如果后续把这条规则写进 `code-rules.md`，建议直接写成：

### 注释直接写清意思

> 注释直接写清当前内容在做什么、为什么这样做，或会带来什么影响。

## 这样做的好处

- `code-rules.md` 和 `comment-rules.md` 的层级更清楚
- 项目级规则不再为选择哪种语言举例而反复摇摆
- 后续迁移其他跨语言注释原则时，能保持一致写法

## 执行检查点

1. `code-rules.md` 继续保持项目级原则句风格
2. 后续迁入“注释直接写清意思”时，只迁规则正文，不迁推荐/不推荐代码示例
3. `comment-rules.md` 继续保留语言级示例职责

## 完成标准

- `code-rules.md` 的默认写法边界被明确下来
- “注释直接写清意思”迁入项目级时的写法被明确下来
- 项目级和语言级规则的示例职责不再混淆
